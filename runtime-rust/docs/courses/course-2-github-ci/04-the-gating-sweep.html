Lesson 4 · the cornerstone job Anatomy of examples-sweep — the gate

This is the job that decides red or green for the whole backend. For every example, on every OS, it does three things: build it on the Rust backend, run it, and check it behaves the same as the Go build. Let's read exactly what that means.

1What one run does, per example

BUILD
--backend rust
+ cargo build
RUN
per shape
cli / server / live / tui / webview
EQUIV
Go ≡ Rust
same behaviour
VERDICT
✓ / ✗
per row

The job itself is small — it builds the Sky compiler, then hands off to a script that loops over the examples:

.github/workflows/examples-sweep.yml (excerpt)

      - name: Run examples sweep
        shell: bash
        run: bash runtime-rust/scripts/examples-sweep.sh

Keeping the logic in a committed script (not inline YAML) means you can run the exact same sweep locally. The YAML just provides the machine.

2"Run" means something different per shape

An example is exercised the way its shape demands — the sweep's lib/checks.sh has one function per shape:

ShapeHow RUN is checked
clirun it; it must finish without panicking; compare stdout
serverboot it; curl a route; compare the HTTP body
liveboot it; drive a real headless-browser scenario; it must pass on both backends
tuidrive it through a pseudo-terminal; it must run without panic
webviewboot it under a virtual display (xvfb); it must not crash
EQUIV is the real test Building proves it compiles; running and comparing against Go proves it's correct. The Go backend is the reference oracle: if Rust's stdout / HTTP body / browser scenario matches Go's, the Rust port is behaving. This is "green ≠ correct" from Course 1 turned into a gate — a build-only check would miss a "the click does nothing" regression.

3What makes the job red

The job fails if — and only if — the sweep prints VERDICT: FAIL, which happens when any row is a genuine failure (build error, panic, hang, or a Go≢Rust difference). Two things are deliberately not failures:

  • SKIP — a shape a host can't run (a TUI needs a real pty; Windows skips the headless browser). An honest "not applicable here", coloured green-neutral.
  • amber go-ref-broken — the Go reference itself is broken for that example (an upstream bug), so there's nothing to compare against.

4The guards around it

  examples-sweep:
    if: github.repository == 'arthurmaciel/sky'   # fork-only — never runs upstream
    env:
      SKY_SWEEP_FORCE: '1'      # skip the local "only at night" gate; CI has no night window
      SKY_NO_SCCACHE: '1'       # sccache's GitHub backend is retired — use actions/cache instead
  • The if: repository guard means this fork-only Rust workflow never runs if someone forks it elsewhere — it's tied to arthurmaciel/sky.
  • Environment toggles adapt the same script to CI: force past the developer-only night-gate, and disable a caching wrapper that doesn't work on GitHub's runners.

5Reading the result

Each matrix job writes a per-OS BUILD·RUN·EQUIV table to the run's summary (and uploads it as the artifact from Lesson 3). That table is the honest, at-a-glance state of the backend on that OS — green rows, SKIP rows, and any red. It's the same table the README mirrors (Lesson 6).

Summary

  • For every example × OS: BUILD (--backend rust + cargo) · RUN (per-shape) · EQUIV (matches the Go reference).
  • RUN differs by shape (cli stdout, server body, live browser scenario, tui pty, webview xvfb); EQUIV is the correctness test.
  • Red only on VERDICT: FAIL; SKIP and amber go-ref-broken are green-neutral.
  • Guarded by a fork-only if: and CI-adapting env; logic lives in a runnable script; results are a per-OS BUILD·RUN·EQUIV table.
