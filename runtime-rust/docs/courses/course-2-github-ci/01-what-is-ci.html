Lesson 1 · from zero What is Continuous Integration?

No prior knowledge needed. By the end of this page you'll know the problem CI solves, the five words you need to read any workflow, and what the little green check on a commit actually means.

1The problem, before CI

You change some code. Does it still build? Do the tests pass? On Linux and macOS and Windows? Did you break an example you weren't even looking at? The honest answer, if you only check by hand, is "probably?" — and "probably" is how broken code reaches other people.

It gets worse with more contributors: everyone runs slightly different machines, forgets a step, or tests only what they touched. Bugs slip in not because people are careless, but because manual checking doesn't scale.

The idea Continuous Integration = every time the code changes, a server automatically builds it and runs the checks — the same checks, the same way, every time. If something breaks, you find out in minutes, on the exact commit that broke it.

You push. GitHub notices and spins up a fresh, clean machine (a "runner"), follows your written recipe step by step, and reports back a green check (everything passed) or a red X (something failed) right next to your commit. Nobody had to remember to do anything.

Why "fresh machine" matters The runner starts from nothing every time. So if the build works there, it works because of what's in your repo — not because of something you happened to have installed locally. CI turns "works on my machine" into "works, period."

3The five words you need

Every GitHub Actions setup is built from these. Learn them once and you can read any workflow file.

WordWhat it is
WorkflowOne YAML file under .github/workflows/ describing automation: when to run and what to do. This repo's is examples-sweep.yml.
Trigger (on:)What starts it — a push, a pull_request, a manual button (workflow_dispatch), or a clock (schedule).
JobA chunk of work that runs on one fresh runner. A workflow can have many; they run in parallel unless one needs another.
StepOne thing inside a job, run top to bottom. Either uses: a prebuilt action, or run: a shell command.
RunnerThe machine a job runs on — e.g. ubuntu-latest. GitHub provides Linux, macOS, and Windows runners.

4What it looks like (this repo)

Here is the top of this project's real workflow — just the "when" and the start of the "what". You already know every keyword:

.github/workflows/examples-sweep.yml (excerpt)

name: Rust examples sweep

on:                          # the triggers
  push:
    branches: [main, 'feat/**']
    paths-ignore: ['**.md']  # docs-only change? skip the heavy sweep
  workflow_dispatch:           # a manual "Run workflow" button
  schedule:
    - cron: '17 6 * * 1'      # every Monday, automatically

jobs:                        # the work
  examples-sweep:
    runs-on: ${{ matrix.os }}   # a fresh ubuntu / macos / windows runner
    steps:
      - uses: actions/checkout@v4   # step 1: grab the code
      - run: bash runtime-rust/scripts/examples-sweep.sh  # step 2: run the sweep

Read it in English: "On every push to main or a feat/* branch (unless only docs changed), or when I click the button, or every Monday — on a fresh Ubuntu/macOS/Windows machine, check out the code and run the sweep script." That's a complete CI pipeline, and you can already follow it.

Notice paths-ignore: ['**.md'] — a real, practical touch. The sweep is expensive, so a commit that only edits Markdown docs skips it. Small details like this are most of what "writing good CI" actually is, and Course 2 is full of them.

5What "green" means (and doesn't)

A green check means: every step the workflow ran finished successfully. It does not automatically mean the code is correct — only that whatever checks you wrote passed. CI is exactly as good as the checks you give it. That's why this repo's sweep doesn't just build — it also runs each example and compares it against the Go reference (you'll meet that in Lesson 4).

6Check yourself

1. What is a "runner"?
2. In examples-sweep.yml, why does paths-ignore: ['**.md'] exist?

Summary

  • CI = a server automatically runs the same checks on every change, on a fresh machine, and reports green/red on the commit.
  • Five words: workflow (the file), trigger (on:), job (work on one runner), step (uses:/run:), runner (the machine).
  • You can already read this repo's on: + first job in plain English.
  • Green means "the checks passed", not "the code is correct" — CI is only as good as its checks.
