Lesson 7 · the capstone Change the CI — without breaking the gate

You now understand every part of this workflow. The final skill is changing it confidently: adding a check, a job, or an OS, and knowing which guardrails you must not trip. This lesson is a checklist you can actually use.

1Three common changes

Add a step (a new check)

Want a lint, a format check, an extra test? Add a step to the relevant job. Make it able to fail — that's what makes it a check:

      - name: Check formatting
        run: cargo fmt --check    # non-zero exit → step fails → job red

Put it before the expensive sweep if it's cheap and likely to fail — fast feedback first.

Add an OS / value to the matrix

One line. The job fans out automatically, and ${{ matrix.os }} already labels artifacts per value, so nothing downstream breaks:

      matrix:
        os: [ubuntu-latest, ubuntu-22.04, macos-latest, windows-latest]

Add a whole job

Copy the shape: runs-on, the toolchain uses: steps, your run:. If it should only run for the right repo/branch, copy the if: guard. If it depends on another job's output, add needs: and download-artifact.

2The guardrails — do not trip these

GuardrailRule
The gate is sacredThe examples-sweep job is the pass/fail gate. Don't make it continue-on-error, and don't move correctness checks into a non-gating job — a green checkmark must still mean "the backend works".
Keep perf non-gatingAnything noisy (benchmarks) stays continue-on-error: true and dispatch/schedule-only. Don't gate on a number that bounces 2× between runs.
Don't loop write-backIf a job pushes, keep all three loop guards: [skip ci], the GITHUB_TOKEN (no extra PAT that would re-trigger), and the paths-ignore on the trigger.
Least privilegeTop-level permissions: contents: read. Grant write only on the one job that needs it.
Logic lives in scriptsReal work belongs in runtime-rust/scripts/ (so it runs locally too); the YAML just provides the machine + env. Don't bury a 40-line bash blob inline.
One source of truthThe example list, the per-shape checks, and the env live in scripts/lib/{examples,checks,env}.sh. Add a new example or a speed flag there, not in a per-runner copy.
Fork-only stays fork-onlyKeep the if: github.repository == 'arthurmaciel/sky' guard so this fork-specific workflow never runs on someone else's fork.

3Test a workflow change without fear

  • Validate the YAML first. A misindented key makes GitHub silently ignore the file. Parse it locally (python3 -c "import yaml,sys; yaml.safe_load(open('…'))") before pushing.
  • Use a feature branch. The push trigger covers feat/**, so your change runs on your branch — not on main.
  • Use the button. For the dispatch-only jobs, click "Run workflow" to test on demand instead of waiting for the cron.
  • Read the job summary + artifacts. They tell you what happened far faster than scrolling raw logs.
A worked example of all this The CI → README automation in Lesson 6 was a real change made to this very workflow: a new update-readme job, scoped contents: write, a weekly schedule added to on:, the three loop guards, and the generator logic kept in a script (readme-tables.py). Every rule on this page is a rule that change had to follow.

4You're done — what you can do now

  • Read any GitHub Actions workflow and explain it in plain English.
  • Write one from scratch — triggers, jobs, steps, matrix, cache, artifacts.
  • Navigate this repo's pipeline: the gating sweep, the dispatch-only perf/static jobs, and the self-updating README — and change it without breaking the gate or looping the bot.

Summary — and course complete 🎉

  • Changes are easy: add a failable step, a matrix value, or a whole job (copy the shape + guards).
  • Guardrails: the sweep gate is sacred; perf stays non-gating; defend the write-back loop; least-privilege permissions; logic in scripts; one source of truth; fork-only guard.
  • Test safely: validate YAML, use a feature branch + the dispatch button, read the summary/artifacts.
  • You can now read, write, and improve this CI.
