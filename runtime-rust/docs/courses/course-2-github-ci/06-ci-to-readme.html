Lesson 6 · CI that writes back The job that updates the README for you

CI usually only reads your repo. This one writes to it: a job downloads the perf + static numbers other jobs measured, regenerates the tables in README.md, and commits the change — automatically. It's the most advanced pattern in this workflow, and it's built from pieces you already know.

1The problem it solves

The README shows tables of results — example status, perf ratios, static binary sizes. Hand-maintained, those go stale within hours of a sweep. The fix: let the machine that produces the numbers also write them, from one source of truth.

Fenced regions = machine-owned Only specific blocks of the README are machine-written, marked with HTML comments: <!-- AUTOGEN:static-table BEGIN --> … END -->. A small script (readme-tables.py) regenerates only what's between the fences; the prose around them stays hand-written. Humans own the words, the machine owns the data tables — no fighting over the same lines.

2The job, piece by piece

.github/workflows/examples-sweep.yml (update-readme)

  update-readme:
    if: … (workflow_dispatch || schedule)
    needs: [examples-sweep, examples-perf-sweep, static-perf]   # A · wait for the data + the gate
    permissions:
      contents: write                                       # B · allowed to push
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4                    # C · grab the perf/static TSVs
        with: { path: artifacts, merge-multiple: true }
      - run: |                                              # D · regenerate the fenced tables
          python3 runtime-rust/scripts/readme-tables.py static   --results artifacts --write
          python3 runtime-rust/scripts/readme-tables.py examples --results artifacts --write
      - run: |                                              # E · commit + push only if changed
          git diff --quiet -- runtime-rust/README.md && exit 0
          git commit -am "docs: auto-sync README tables [skip ci]"
          git push
PieceWhy
Aneeds:Run only after the data jobs finish — and after the gate. examples-sweep in needs means a RED sweep skips this job, so the README never publishes a false "all green".
Bpermissions: contents: writeBy default a job can only read. To push, it must be granted write — scoped to this job only, not the whole workflow.
Cdownload-artifactThe numbers were measured in other jobs (Lesson 5) and uploaded as artifacts (Lesson 3). This is the cross-job hand-off.
Dreadme-tables.py … --writeRegenerate only the fenced regions from the fresh TSVs.
Ecommit + pushOnly if something actually changed (git diff --quiet), so empty runs don't spam commits.

3The trap: an infinite loop

A job that pushes a commit could trigger the workflow again… which pushes again… forever. This is the danger of write-back CI, and it's defended three ways:

  • [skip ci] in the commit message — GitHub skips workflows for commits marked this way.
  • The token rule — pushes made with the automatic GITHUB_TOKEN do not, by design, trigger further workflows. (No recursion by default.)
  • paths-ignore: ['**.md'] — the commit only touches README.md, and the push trigger ignores Markdown-only changes.
Belt and braces Any one of these would stop the loop; the workflow uses all three. With write-back automation, defend the loop redundantly — a runaway CI commit storm is embarrassing and burns minutes fast.

Summary

  • Only fenced README regions are machine-written (AUTOGEN:…); prose stays human.
  • The job needs the data jobs and the gate, gets contents: write, download-artifacts the TSVs, regenerates via readme-tables.py --write, and commits only on a real diff.
  • The loop is defended three ways: [skip ci], the GITHUB_TOKEN no-recursion rule, and paths-ignore.
