Lesson 2 · hands-on Your first workflow, line by line

In Lesson 1 you learned the five words. Now you'll read — and could write — a complete, working GitHub Actions workflow. It's smaller than you'd guess: a name, a trigger, and a job with a couple of steps.

1The whole thing

Save this as .github/workflows/hello.yml in any repo and it runs. Every line is labelled; we'll unpack them below.

.github/workflows/hello.yml

name: Hello CI              # A · what it's called (shown in the Actions tab)

on: [push]                 # B · the trigger — run on every push

jobs:                       # C · the work (one or more jobs)
  greet:                     #     a job, named "greet"
    runs-on: ubuntu-latest    # D · the runner (a fresh Ubuntu machine)
    steps:                    # E · the steps, run top to bottom
      - uses: actions/checkout@v4        # F · a prebuilt action: clone the repo
      - name: Say hello
        run: echo "Hello from CI on $(uname -s)!"  # G · a shell command

2Reading it, label by label

LabelKeyWhat it does
Aname:A human label for the workflow. Optional but nice — it's what you see in the repo's Actions tab.
Bon:The trigger. [push] means "run on every push to any branch". (Lesson 1's repo example used the longer form with branch + path filters.)
Cjobs:The container for work. Everything indented under here is one or more jobs.
—greet:A job, with an id you choose. A workflow can have many; they run in parallel by default.
Druns-on:Which runner to use. ubuntu-latest / macos-latest / windows-latest are GitHub-hosted.
Esteps:An ordered list. Each step runs after the previous one finishes; if one fails, the job stops and goes red.
Fuses:Run a prebuilt action — reusable automation someone published. actions/checkout@v4 clones your repo onto the runner (almost every workflow starts with it).
Grun:Run a shell command, exactly as you would in a terminal on that runner.
The one rule of steps Every step is either uses: (someone else's packaged action) or run: (your own shell command) — never both. Reach for uses: for common chores (checkout, install a language, cache, upload), and run: for "do my actual thing".

4Two upgrades you'll always want

Add a real check (the point of CI)

A greeting proves the pipeline runs; a check makes it useful. Replace the echo with something that can fail — and CI becomes a safety net:

      - uses: actions/checkout@v4
      - name: Install a toolchain
        uses: dtolnay/rust-toolchain@stable   # prebuilt: installs Rust
      - name: Build & test
        run: |                              # "|" lets you write multiple lines
          cargo build
          cargo test

If cargo build or cargo test exits non-zero, the step fails, the job goes red, and the commit is flagged. That's the whole game.

Add a manual button + control when it runs

The short on: [push] grows into the structured form you saw in Lesson 1 — adding a manual trigger and skipping docs-only pushes:

on:
  push:
    branches: [main]
    paths-ignore: ['**.md']   # skip when only docs changed
  workflow_dispatch:           # adds a "Run workflow" button in the UI
YAML gotcha Indentation is meaningful in YAML (like Sky and Python) — spaces only, never tabs. A misindented key is the #1 reason a workflow "doesn't run": GitHub silently ignores a file it can't parse. When in doubt, copy the indentation of a working file exactly.

Summary

  • A workflow is a name + on (trigger) + jobs; a job is runs-on (runner) + steps.
  • Every step is uses: (a prebuilt action like checkout) or run: (a shell command) — never both.
  • CI becomes useful when a step can fail (a build/test). A failing step → red job → flagged commit.
  • Grow on: [push] into branch + paths-ignore filters and a workflow_dispatch button. YAML is space-indented — no tabs.
