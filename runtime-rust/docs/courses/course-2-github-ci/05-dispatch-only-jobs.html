Lesson 5 · run it on purpose Perf & static-perf — the deliberate, non-gating jobs

Not every check belongs on every push. Performance benchmarks are noisy on shared runners and slow. This repo runs them only when you ask (a button) or on a weekly clock — and never lets them fail the build. Here's why, and how that's expressed.

1The problem with benchmarks on every push

  • Noisy. GitHub runners are shared VMs with no CPU pinning — the same benchmark can swing wildly run to run. A throughput number that bounces 2× isn't a reliable gate.
  • Slow. Building every example in release mode, on three OSes, plus the Go reference, takes a long time.

So perf is measured and archived, never used to pass/fail. The gate stays the fast, deterministic sweep (Lesson 4).

2Triggering on purpose, not on push

Two jobs — examples-perf-sweep (throughput/RSS/cold-start) and static-perf (static-binary sizes across 3 OSes) — share a guard that runs them only on a manual button or the weekly cron:

.github/workflows/examples-sweep.yml (excerpt)

  examples-perf-sweep:
    if: github.repository == 'arthurmaciel/sky'
        && (github.event_name == 'workflow_dispatch' || github.event_name == 'schedule')
    continue-on-error: true        # never fails the overall workflow
    timeout-minutes: 330          # a hard ceiling well under GitHub's 6h limit

Recall the triggers from Lesson 1: this workflow's on: includes workflow_dispatch (the "Run workflow" button) and a schedule: cron: '17 6 * * 1' (Mondays). The push trigger is excluded by the if:, so a normal commit never starts these.

continue-on-error: true This is what "non-gating" means in YAML. The job still runs and reports, but even if it fails, the workflow is considered successful. Perf is information, not a verdict — you read it, you don't let it block a merge.

3What each measures

JobMeasuresWhere
examples-perf-sweepRust-vs-Go throughput, resident memory (RSS), cold-start, binary sizeubuntu only
static-perffully-static binary size (musl) + the static-vs-dynamic comparison; Linux also runs throughput/RSSa 3-OS matrix (Linux native, Windows native, macOS cross-compiles a Linux binary)

Both upload their numbers as artifacts (TSV files) — and, like the sweep, the heavy lifting is in committed scripts (examples-perf-sweep.sh, static-perf.sh), so you can run them locally too.

4Why a weekly schedule at all?

So the numbers don't rot. Without a cadence, the perf table in the README would reflect whenever someone last clicked the button — maybe weeks ago. The Monday cron keeps it fresh automatically. (One subtlety the workflow handles: scheduled runs fire from the repo's default branch, so these jobs force ref: feat/runtime-rust to operate on the Rust branch.)

Scheduled workflows run from the default branch A schedule: only triggers using the workflow file as it exists on the repository's default branch. If your work lives on a feature branch, either the workflow must also be on the default branch, or — as here — the jobs explicitly check out the branch they mean to test. A common, surprising gotcha.

5The shape so far

One gating job on every push (the sweep), and two informational jobs you run deliberately (perf + static). The perf artifacts they produce don't just sit there — the next job picks them up and writes them into the README, which is Lesson 6.

Summary

  • Perf is noisy + slow, so it's measured, not gated: continue-on-error: true.
  • Triggered only via workflow_dispatch or a weekly schedule — excluded from push by the job's if:.
  • examples-perf-sweep (throughput/RSS/cold/size, ubuntu) and static-perf (static sizes, 3-OS) upload TSV artifacts via runnable scripts.
  • Scheduled runs fire from the default branch — the jobs force the Rust branch explicitly.
