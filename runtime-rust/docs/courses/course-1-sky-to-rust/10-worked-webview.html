Lesson 10 · TEA on the desktop Worked shape — Sky.Webview ×2

The last shape: a native desktop window. Sky.Webview is — predictably now — the same TEA, rendered into a system webview (WebKit / WebView2) via the wry/tao crates. Same Html view as Sky.Live; the only new thing is a window config.

An honest note on grounding The real wry/tao window links the system WebKit development libraries, which aren't installed on the machine these courses were built on — so unlike Lessons 6–9, this lesson isn't traced from a freshly-built main.rs. Instead it's grounded in (a) the example's Sky source, (b) the lowering rules you've already verified, and (c) a real runtime-level Rust example checked into the repo. Where something is shown by pattern rather than a fresh build, it's flagged.

AThe Sky shape

examples/31-webview-stopwatch-ui / Std.Webview shape

import Std.Webview as Webview

main =
    Webview.app
        { init = init, update = update, view = view
        , subscriptions = subscriptions
        , window = { title = "Sky App", size = ( 800, 600 ) }
        }
        |> Task.run

Identical to Sky.Live except: no routes, and a window record (title + size). The view produces the same Html tree — in fact Sky.Webview reuses Sky.Live's renderer, so one view function paints in a browser (Live) or a desktop window (Webview) unchanged.

BThe lowering (by the established rules)

Webview.app { … } |> Task.run routes to the webview_app kernel, wrapped by task_run (the |> Task.run entry shape from Lesson 6). The window record becomes a WebviewWindowCfg struct. init/ update/view/subscriptions lower exactly as in Lessons 6 and 8.

CA real runtime-level proof

The repo ships a hand-written Rust smoke test that exercises the exact runtime API the codegen targets — so even without building an example, you can see the real shape webview_app expects:

runtime-rust/examples/webview_smoke.rs (real, trimmed)

fn view(n: i64) -> Html<i64> {
    Html::HElement("div".into(), vec![], vec![
        Html::HElement("button".into(),
            vec![Attribute::EventAttr(Event::OnMsg("click".into(), n + 1))],
            vec![Html::HText("increment".into())]),
    ])
}

fn main() {
    let task = webview_app::<i64, i64, String, _, _, _, _>(
        |()| (0i64, SkyCmd::None),         // init
        |msg, _model| (msg, SkyCmd::None), // update
        view,                            // view
        |_m| SkySub::None,               // subscriptions
        WebviewWindowCfg { title: "Sky Webview smoke".into(), size: (420, 280) },
    );
    let _ = block_on(task);
}

This is exactly what the codegen produces in spirit: the five TEA values + a WebviewWindowCfg, passed to webview_app, driven by block_on. The view builds the same Html the Live backend uses (HElement / HText / EventAttr / OnMsg), which is why one Sky view serves both.

DThe build flip you should know

cgo / cargo features When a project uses Sky.Webview, the build runner switches the cargo build to enable the webview feature (which pulls in wry/tao and needs the system WebKit libs). On a host without those libs, a non-webview project still builds fine because the feature is gated off (Lesson 4's feature-gating in action) — and a stub keeps non-webview platforms linking.

Summary — all five shapes done

  • Sky.Webview = TEA + a window cfg, entry webview_app, same Html view as Live (shared renderer).
  • Webview.app{…} |> Task.run → task_run(webview_app(init, update, view, subs, WebviewWindowCfg{…})).
  • The real runtime API is proven by runtime-rust/examples/webview_smoke.rs; the window build needs system WebKit + the webview cargo feature.
  • Five shapes, one lowering — only the entry kernel + view type + extra handler differ.
