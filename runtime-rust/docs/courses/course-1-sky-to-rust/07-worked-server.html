Lesson 7 · routes, handlers, the Task boundary Worked shape — HTTP server ×2

A server is a list of routes, each a handler that takes a Request and returns a Task of a Response. We trace a full REST server into its real Rust, then a streaming (SSE) server — both built with sky build --backend rust.

AExample 1 — 15-http-server

examples/15-http-server/src/Main.sky (trimmed)

import Sky.Http.Server exposing (Request, Response, Handler)

main =
    Server.listen 8000
        [ Server.get "/" handleHome
        , Server.get "/hello/:name" handleHello
        , Server.post "/api/echo" handleEcho
        ]

handleHello : Handler          -- = Request -> Task Error Response
handleHello req =
    case Server.param "name" req of
        Just name -> Task.succeed (Server.text ("Hello, " ++ name ++ "!"))
        Nothing   -> Task.succeed (Server.text "Hello, stranger!")

The routes lower to a vector of server_get / server_post

examples/15-http-server/sky-out/Rust/src/main.rs (real, trimmed)

pub fn sky_main() -> SkyTask<()> {
    server_listen::<SkyError>(
        8000,
        vec![
            server_get::<SkyError, _>("/".to_string(), main_handle_home),
            server_get::<SkyError, _>("/hello/:name".to_string(), main_handle_hello),
            server_post::<SkyError, _>("/api/echo".to_string(), main_handle_echo),
        ],
    )
}

The route list becomes a Rust vec![]; each Server.get / Server.post routes (via kernelToRust) to server_get / server_post, passing the path string and the handler function by name.

A handler is Request → Task Response

pub fn main_handle_hello(req: SkyHttpServerRequest) -> SkyTask<SkyHttpServerResponse> {
    let name = match server_param("name".to_string(), req) {
        SkyMaybe::Just(n)  => n,
        SkyMaybe::Nothing => "stranger".to_string(),
    };
    task_succeed(server_text(format!("{}{}", "Hello, ".to_string(),
        format!("{}{}", name, "!".to_string()))))
}

Several lowerings at once:

  • The Handler alias is Request → Task Error Response, so the Rust fn is fn(SkyHttpServerRequest) -> SkyTask<SkyHttpServerResponse>.
  • Server.param "name" req → server_param("name".to_string(), req), returning a SkyMaybe; the Sky case on it → a Rust match over SkyMaybe::Just/Nothing.
  • ++ string concat → nested format!("{}{}", a, b).
  • Task.succeed (Server.text …) → task_succeed(server_text(…)).
The SkyTask alias, demystified Every generated project defines pub type SkyTask<A> = sky_runtime::SkyTask<SkyError, A>;. That's why you see one-parameter SkyTask<Response> in the output even though the runtime's task has an error parameter too — the error is fixed to SkyError at the alias. And Handler itself is Arc<dyn Fn(Request) -> SkyTask<Response> + Send + Sync> so handlers can be stored and shared across the async server.

Entry

Server.listen returns a Task, so this is the bare-Task shape from Lesson 6: sky_main() -> SkyTask<()>, and the real fn main() drives it with block_on (which spins up the async server and blocks until it stops).

BExample 2 — 30-sse-server-demo (streaming)

Same skeleton, but one route streams Server-Sent Events instead of returning a single body. It uses Sky.Http.Server.Stream:

examples/30-sse-server-demo/src/Main.sky (trimmed)

import Sky.Http.Server.Stream as Stream

main =
    Server.listen 8000
        [ Server.get "/" handleHome, Server.get "/events" handleEvents ]

handleEvents req =
    Stream.stream "text/event-stream"
        (\writer ->
            emitTick writer 1 |> Task.andThen (\_ -> emitTick writer 2)
                |> Task.andThen (\_ -> Stream.finish writer))

emitTick : Stream.StreamWriter -> Int -> Task Error ()
emitTick writer n =
    Stream.emit ("event: tick\ndata: " ++ String.fromInt n ++ "\n\n") writer

It builds clean on the Rust backend (the runtime pulls in its sky_http_server_stream module on demand — Lesson 4's feature gating). The lowering uses only patterns you've already met:

SkyRust
Stream.stream "…" (\writer -> …)stream_stream("…".to_string(), |writer| …) (lambda → closure)
Stream.emit s writer / Stream.finish writerstream_emit(s, writer) / stream_finish(writer)
a |> Task.andThen (\_ -> b)task_and_then(a, |_| b) — the chained effects
emitTick : StreamWriter -> Int -> Task Error ()fn main_emit_tick(writer: …, n: i64) -> SkyTask<()>
Why both fit the same model A normal handler returns Task Response (one body); a streaming handler returns a Task too, but its body writes chunks through a StreamWriter over time. Same Task boundary, same server_listen entry — only the handler's shape differs. That's the power of "every effect is a Task": one model covers request/response and streaming alike.

CThe server pattern, generalised

  • A route list → a vec![] of server_get/server_post(path, handler-fn).
  • A Handler → fn(SkyHttpServerRequest) -> SkyTask<SkyHttpServerResponse>.
  • Extractors/responses are kernels: server_param, server_text/server_html/server_json, server_with_header, server_get_cookie.
  • Server.listen is a bare Task → block_on entry (Lesson 6).

Summary

  • Routes → vec![server_get/server_post(path, handler)]; Server.listen → bare-Task block_on entry.
  • A Handler → fn(Request) -> SkyTask<Response>; extractors/responses are server_* kernels; case on Server.param → match on SkyMaybe.
  • The SkyTask<A> alias fixes the error to SkyError; Handler is an Arc<dyn Fn…>.
  • Streaming (SSE) is the same Task boundary — the body writes chunks via a StreamWriter.
