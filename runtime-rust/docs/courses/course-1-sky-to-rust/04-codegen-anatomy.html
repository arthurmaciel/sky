Lesson 4 · stage 4, opened up Codegen anatomy: the Builder/ modules

Stage 4 — lowering the typed canonical AST to Rust text — is one orchestrator plus eleven focused modules under src/Sky/Generate/Rust/Builder/. This lesson is the map: who owns what, and the order they run in.

1The orchestrator

The whole Rust project is produced by generateRustProject. It calls the core engine generateRust, then writes the files: main.rs, one .rs per module, sky_runtime/mod.rs (assembled from only the runtime modules this program uses), Cargo.toml, the copied runtime crate, and any FFI bindings.

Entry: src/Sky/Generate/Rust/Project.hs · generateRustProject (called from src/Sky/Build/Compile.hs). It copies runtime-rust/src/sky_runtime/ via copyRustRuntime.

2The call flow

From program down to a single expression, the lowering nests like this:

buildProgram            -- ModuleEmitter.hs — all modules; detect `main`; build type map
 └─ buildModule         -- one module → Rust items
     └─ declsToRustItems  -- declarations → [RustItem]
         └─ defToRustItem  -- one definition → a Rust fn (sig + body)
             └─ exprToRustString   -- ExprEmitter.hs — one expression → Rust text
                 └─ kernelToRust   -- Kernel.hs — a kernel call → a runtime fn name

3The eleven modules

Grouped by what they do. Open them alongside — src/Sky/Generate/Rust/Builder/.

Driving the walk

ModuleOwns
ModuleEmitter.hsThe top of the walk. buildProgram coordinates all modules, builds the record/ADT name map, detects main and whether its tail is a Task (→ block_on), and handles name-collision renaming. buildModule emits one module's declarations.
ExprEmitter.hsThe largest module (~3.8k lines). Turns one expression into Rust text: exprToRustString / exprToRustInner handle calls, kernels, binops, literals, closures, currying, and the deferred-effect let _ = case.
Pattern.hsLowers patterns — a case arm or a destructuring parameter — to Rust match/param syntax, and lists the variables a pattern binds.

Resolving names & types

ModuleOwns
Kernel.hsKernel routing — kernelToRust (module, name) → "rust_fn". The single source of truth mapping every stdlib call to its runtime function. (Lesson 5 is all about this.)
TypeRenderer.hsRenders a Sky Can.Type as a Rust type string — typeToRustString (Int → i64, Task _ a → SkyTask<…>, function types → closures). Also peels arrow types into params + return.
TypeEmitter.hsEmits user type definitions: Sky unions → Rust enums, record aliases → structs, with derives + a SkyStringify impl.
Naming.hsName mangling — toSnakeCase (fromInt → from_int), module-path mangling, and escaping Rust keywords (type → type_).
SigRegistry.hsHard-coded Rust signatures for known runtime fns — used to pin generic type parameters on a call when the args' types alone don't fix them.

Collecting & assembling

ModuleOwns
Walker.hsA metadata pre-pass. Scans the AST to find which kernels are used (→ Cargo features), which defs take zero args, and what record shapes exist. Runs before emission so the rest knows what to turn on.
Types.hsThe data structures: RustBuilder (accumulated output), EmitCtx (the per-expression context — solved types, clone hints, record map), and UsedKernels (the feature-gate flags).
Emitter.hsThe finish line. emitRust formats the accumulated RustBuilder into the final main.rs + module files; emitCargoToml writes Cargo.toml with only the feature-gated deps the program needs.

4Two ideas worth holding onto

EmitCtx — the context that travels As codegen walks the tree, it carries an EmitCtx (Types.hs): the solved types, the record-name map, and hints like "which variables are used twice and therefore need .clone()". This is how a deeply-nested expression still knows its types and how to render them. When you read ExprEmitter, watch the EmitCtx thread through every function.
Walker first → a small binary Because Walker.hs records exactly which capabilities a program uses, Emitter.hs can turn off everything it doesn't. A CLI program never pulls in axum, sqlx, or tokio's heavy features — the generated Cargo.toml omits them entirely. That's why a hello-world compiles fast and links small, while a Sky.Live app pulls the web stack. Same codegen, different feature set, decided by the pre-pass.

5Where the example landed

Back to main = println (String.fromInt (1 + 2)): buildProgram saw a single module with one Task-tailed main; ExprEmitter lowered the body, routing String.fromInt via kernelToRust and special-casing println; TypeRenderer turned Task Error () into SkyTask<SkyError, ()>; Emitter wrapped it in sky_main + a block_on main and wrote a tiny Cargo.toml (no web/db features). Walker had already noted it uses only basic kernels.

Summary

  • One orchestrator (generateRustProject) + eleven focused modules under Builder/.
  • The walk: buildProgram → buildModule → declsToRustItems → defToRustItem → exprToRustString → kernelToRust.
  • Roles: drive the walk (ModuleEmitter / ExprEmitter / Pattern), resolve names+types (Kernel / TypeRenderer / TypeEmitter / Naming / SigRegistry), collect+assemble (Walker / Types / Emitter).
  • EmitCtx threads context through; Walker's pre-pass drives feature gates so binaries stay small.
