Lesson 8 · TEA on the web Worked shape — Sky.Live ×2

Sky.Live is The Elm Architecture, served over HTTP with live updates. You already know the shape from Lesson 6 (init/update/view/subscriptions) — here the view produces HTML, and the entry is a whole web server. We trace the real Rust of a counter, then point at a full app.

AExample 1 — 09-live-counter

examples/09-live-counter/src/Main.sky (trimmed)

import Std.Html exposing (..)
import Std.Html.Events exposing (onClick)

main =
    Live.app
        { init = init, update = update, view = view
        , subscriptions = subscriptions
        , routes = [ route "/" CounterPage, route "/about" AboutPage ]
        }

view model =
    div []
        [ nav [ class "navbar" ]
            [ button [ onClick (Navigate CounterPage) ] [ text "Counter" ]
            , button [ onClick (Navigate AboutPage) ]   [ text "About" ]
            ]
        , …
        ]

The view lowers to an Html tree of std_html_* calls

examples/09-live-counter/sky-out/Rust/src/main.rs (real, trimmed)

pub fn main_view(model: MainModel) -> StdHtmlHtml<MainMsg> {
    std_html_div(
        vec![],
        vec![
            std_html_nav(
                vec![std_html_attributes_class("navbar".to_string())],
                vec![
                    std_html_button( /* onClick(Navigate(…)) attr + children */ ),
                    …
                ],
            ),
        ],
    )
}

Key points:

  • The view returns StdHtmlHtml<MainMsg> — an HTML tree parameterised by your Msg type, so a click attribute carries a typed MainMsg.
  • Each HTML builder (div, nav, button, text, class) routes to a std_html_* kernel, taking vec![attrs] and vec![children].
  • init, update, Msg, Model lower exactly like the CLI in Lesson 6 — it's the same TEA.

The entry is a routed web app

pub fn sky_main() -> SkyTask<()> {
    live_app_routed::<SkyError, _, _, _, _, _, _, _, _>(
        main_init, main_update, main_view, main_subscriptions, /* routes, cfg… */
    )
}
fn main() { match block_on(sky_main()) { … } }

Live.app with a routes field routes to live_app_routed (without routes it would be live_app). It returns a bare Task, so — like the server in Lesson 7 — the entry drives it with block_on, which starts the HTTP server, the SSE update channel, and the session store.

The big realisation CLI, Live, Tui, and Webview are the same program with different runtimes. Identical init/update/view/subscriptions; only the entry kernel differs (cli_program / live_app / tui_app / webview_app) and the view's output type (String for a text CLI/TUI, Html for Live/Webview). Learn one, you've learned all four.

BExample 2 — 19-skyforum (a real app)

A full forum: posts, comments, a database, forms, multiple pages. It's split across several modules (a Std.Ui-heavy app must be, to keep the type-checker happy), but every module lowers by the same rules — its State.sky types become enums/structs, its Update.sky becomes match functions, its view modules become std_html_* / ui_* trees, and Main.sky wires Live.app → live_app_routed.

It builds and passes the equivalence sweep (Course 2, Lesson 4): the headless browser drives the same scenario on both the Go and Rust builds and they behave identically. The difference from the counter is scale, not mechanism — DB calls become db_* kernels (Task-typed), forms decode into typed records, but the lowering rules are the ones you already know.

Why split a Live app into modules? A single file with ~25+ polymorphic Html msg/Element msg helpers can blow the HM type-checker's heap. So real Live apps split into State / Update / View/* / Main. This is a Sky front-end constraint, not a Rust-codegen one — but it's why the worked example here is the small counter, with the big one described.

CThe Live pattern, generalised

  • Same TEA as the CLI: Msg→enum, Model→struct, update→match.
  • view : Model -> Html Msg → fn main_view(model) -> StdHtmlHtml<Msg>, an std_html_* tree.
  • Live.app { routes = … } → live_app_routed; bare Task → block_on entry that boots HTTP + SSE + sessions.
  • Persistence/forms are just more Task-typed kernels (db_*) and typed-record decoding.

Summary

  • Sky.Live is TEA over HTTP: same init/update/view/subscriptions as the CLI, but view → Html Msg → StdHtmlHtml<Msg> (a tree of std_html_* calls).
  • Live.app { routes } → live_app_routed, a bare Task driven by block_on (boots HTTP + SSE + sessions).
  • CLI / Live / Tui / Webview = one program, four runtimes — only the entry kernel + view type differ.
  • Real apps (19-skyforum) add scale (DB, forms, modules) but no new lowering rules.
