Lesson 3 · stages 1–3 The front end: parse → canonicalise → type-solve

These three stages are shared with Sky's Go backend — the Rust backend reuses them untouched. Understanding them matters because they hand codegen everything it needs: a fully-resolved, fully-typed tree with no guesswork left.

The handoff Codegen (Lesson 4) never re-derives names or types. It trusts that by the time it runs, "println" is already "the Log kernel" and "1 + 2" is already known to be an Int. The front end's whole job is to make that trust safe.

1Stage 1 — Lex & Parse

Two sub-steps:

  • Lexing turns raw text into a flat token stream — keywords, identifiers, operators, literals. A crucial extra: Sky is indentation-sensitive (like Haskell/Python), so a layout pass converts indentation into explicit structure tokens. That's why you don't write braces.
  • Parsing assembles tokens into the source AST — a tree of declarations and expressions. Names are still bare strings; nothing is resolved.

Entry: src/Sky/Parse/Module.hs · parseModule :: Text → Either ModuleError Src.Module. Lexer/layout: src/Sky/Parse/{Space,Keyword,Primitives}.hs; expression/declaration grammar: src/Sky/Parse/{Expression,Declaration}.hs.

For main = println (String.fromInt (1 + 2)), the source AST is a Def "main" whose body is a Call of the bare name println applied to a Call of String.fromInt applied to a Binop "+". Same tree shape as the canonical one — only the name nodes differ, which is the next stage's job.

2Stage 2 — Canonicalise (name resolution)

This is where bare names become precise references. The canonicaliser walks the tree with knowledge of the module's imports and the symbols its dependencies export, and rewrites each name to exactly one of:

Resolved nodeWhen
Can.VarKernel mod nameThe name is a built-in stdlib kernel — println → ("Log","println"), String.fromInt → ("String","fromInt").
Can.VarTopLevel mod nameA top-level function defined in some module (yours, or stdlib written in Sky).
Can.VarLocal nameA function parameter or a let binding currently in scope.

It also resolves union/record types and cross-module constructors (so an imported type Color = Red | Green exposes Red as a real constructor), and expands type aliases.

Entry: src/Sky/Canonicalise/Module.hs · canonicaliseWithDeps :: Map String DepInfo → Src.Module → Either String Can.Module.

Why this matters for Rust The VarKernel vs VarTopLevel distinction is load-bearing in codegen. A VarKernel goes straight through the kernelToRust table; a VarTopLevel might be a Sky-written stdlib function that's actually an Ffi.kernel alias — a recurring source of "type-checks but cargo-fails" bugs when codegen handles only one of the two. (You'll see this pattern named in Lesson 5.)

3Stage 3 — Type-solve (Hindley–Milner)

Sky requires almost no type annotations because it infers them. The solver uses Hindley–Milner: it walks the tree assigning each expression a fresh type variable, generates equations ("constraints") from how expressions are used, and then unifies — solving those equations with a union-find structure until every variable has a concrete type (or an error if they can't be reconciled).

For our example the constraints resolve cleanly:

1            : Int            -- integer literal
2            : Int
1 + 2        : Int            -- (+) : Int -> Int -> Int
String.fromInt : Int -> String
fromInt (…)  : String
println (…)  : Task Error ()  -- so main : Task Error ()

The output is the SolvedTypes record. Two parts of it matter to codegen:

  • The environment (_stEnv): every name → its final type. This is how codegen knows main returns a Task and must be run with block_on.
  • Region types: a source location → the type inferred there. This lets codegen ask "what is the type of the expression at this exact spot?"

Entry: src/Sky/Type/Solve.hs · solve…; the SolvedTypes record (env + region map, with per-module snapshots). Unification: Sky.Type.Unify + a union-find.

Why region types, not just the environment? Some Rust output can't be chosen from a name alone. The classic case is an empty collection: [] in List Int position must become Vec::<i64>::new(), but [] in List String position needs Vec::<String>. The name "[]" doesn't tell you which — but the region (the exact spot in the source) does, because the solver pinned a concrete type there. Region types are how codegen turbofishes the right Rust type. The same trick drives closure and generic inference.

Summary

  • Lex+Parse → source AST (layout makes indentation structural; names still bare).
  • Canonicalise → resolves every name to VarKernel / VarTopLevel / VarLocal; the kernel-vs-toplevel split matters in codegen.
  • Type-solve (HM) → SolvedTypes: a name→type environment and region types (location→type) that let codegen pick exact Rust types.
  • All three are shared with Go; codegen trusts their output completely.
