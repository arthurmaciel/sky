Lesson 6 · whole programs, real output Worked shape — CLI ×2

Theory becomes concrete here. We take two complete CLI programs and show their actual emitted Rust — produced by sky build --backend rust, not invented. First the simplest possible effect; then a full TEA-style interactive CLI.

All code here is real Every Rust block below was copied from sky-out/Rust/src/main.rs after building the example (lightly trimmed for length). Build it yourself and compare.

AExample 1 — 01-hello-world

examples/01-hello-world/src/Main.sky

module Main exposing (main)
import Std.Log exposing (println)

main =
    println "Hello from Sky!"

Its main has type Task Error () (a bare effect). The emitted Rust:

examples/01-hello-world/sky-out/Rust/src/main.rs (trimmed)

// a thin local wrapper forwards into the runtime crate
pub fn log_println(msg: String) -> SkyTask<()> {
    sky_runtime::log::log_println(msg)
}

pub fn sky_main() -> SkyTask<()> {
    log_println("Hello from Sky!".to_string())
}

fn main() {
    match block_on(sky_main()) {
        SkyResult::Ok(_) => (),
        SkyResult::Err(e) => {
            eprintln!("{:?}", e);
            std::process::exit(1);
        }
    }
}

Read it top to bottom:

  • The "Hello from Sky!" literal gains .to_string() (Sky String → Rust String).
  • println routed (via kernelToRust, Lesson 5) to log_println — a local wrapper that forwards to sky_runtime::log::log_println.
  • main's Task becomes sky_main() -> SkyTask<()> — a value, not yet run.
  • The real fn main() drives it with block_on and turns the SkyResult into an exit code. This is where the effect actually fires.

BExample 2 — 20-cli-counter (TEA on the CLI)

A real interactive program: type +/-/r/q to drive a counter. It uses Sky.Cli — the same init/update/view/subscriptions shape as Sky.Live, plus onLine mapping each stdin line to a Msg.

examples/20-cli-counter/src/Main.sky (trimmed)

type Msg = Increment | Decrement | Reset | Quit | NoOp
type alias Model = { count : Int }

update msg model =
    case msg of
        Increment -> ( { model | count = model.count + 1 }, Cmd.none )
        Decrement -> ( { model | count = model.count - 1 }, Cmd.none )
        Reset     -> ( { count = 0 }, Cmd.none )
        Quit      -> ( model, Cmd.perform (System.exit 0) (\_ -> NoOp) )
        NoOp      -> ( model, Cmd.none )

main =
    Cli.program { init = init, update = update, view = view
               , subscriptions = subscriptions, onLine = onLine }
        |> Task.run

The type definitions lower to Rust enums + structs

pub enum MainMsg { Increment, Decrement, Reset, Quit, NoOp }
impl SkyStringify for MainMsg { /* … "Increment".to_string() … */ }

pub struct MainModel { pub count: i64 }

A Sky type → Rust enum; a record type alias → Rust struct (Int → i64). Each variant also gets a SkyStringify impl (Lesson 2's autoref phase).

Each TEA function becomes a Rust function

pub fn main_init(_: ()) -> (MainModel, SkyCmd<MainMsg>) { … }
pub fn main_view(model: MainModel) -> String {
    // "count=" ++ String.fromInt model.count ++ …
    … string_from_int(model.count) …
}
pub fn main_on_line(line: String) -> MainMsg { /* match String.trim line */ }

The interesting bit: record update + case

{ model | count = model.count + 1 } can't mutate in place (Sky is pure), so codegen clones, sets the field, and returns the clone:

pub fn main_update(msg: MainMsg, model: MainModel) -> (MainModel, SkyCmd<MainMsg>) {
    match msg {
        MainMsg::Increment => (
            {
                let mut __rec = model.clone();
                __rec.count = (model.clone().count + 1);
                __rec
            },
            cmd_none(),
        ),
        MainMsg::Reset => (MainModel { count: 0 }, cmd_none()),
        MainMsg::Quit => (
            model.clone(),
            cmd_perform::<SkyError, i64, _, _>(system_exit(0), |_| MainMsg::NoOp),
        ),
        MainMsg::NoOp => (model.clone(), cmd_none()),
    }
}

A Sky case → Rust match; Cmd.none → cmd_none(); Cmd.perform (System.exit 0) (\_ -> NoOp) → cmd_perform::<…>(system_exit(0), |_| MainMsg::NoOp) (the lambda becomes a Rust closure).

The entry point — and a key contrast with Example 1

pub fn sky_main() -> SkyResult<SkyError, ()> {
    task_run::<SkyError, _>(cli_program(
        main_init, main_update, main_view, main_subscriptions, main_on_line,
    ))
}

fn main() { sky_main(); }
Why is this entry different from Example 1? Example 1's main was a bare Task, so sky_main returned a SkyTask value and the real fn main() drove it with block_on. Here the Sky source ends in |> Task.run, so codegen routes Task.run → task_run inside sky_main — it already runs the program and returns a SkyResult. So fn main() just calls it. Same idea (a Task only runs when driven), two surface shapes — decided by whether the Sky source drives it itself.

Summary

  • A bare effect (main = println …) → sky_main() -> SkyTask<()> driven by block_on in fn main().
  • A TEA CLI lowers each piece: type→enum, record alias→struct, case→match, record update→clone-set-return, lambda→closure.
  • |> Task.run moves the "drive" inside sky_main (task_run), so fn main() just calls it — the entry's shape follows the source.
