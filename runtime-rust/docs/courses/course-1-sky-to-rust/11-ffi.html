Lesson 11 · reaching the crate ecosystem FFI — binding real Rust crates, automatically

Sky's standard library is large, but the real prize is Rust's ecosystem. Sky's FFI is automatic: point sky.toml at a crate and the compiler generates the bindings — no hand-written glue. This lesson covers how that works, what it can and can't reach, and the pattern for the crates it can't.

1How automatic FFI works

You declare a dependency:

sky.toml

["rust.dependencies"]
uuid  = "1.16.0"
serde = { version = "1", features = ["derive"] }

At build time the compiler runs the crate through Rust's own documentation tool — cargo +nightly rustdoc --output-format json — to get a machine description of every public function and type. An inspector (tools/sky-ffi-inspect-rs) reads that JSON and, for each function it can represent, generates a Sky binding. The artifacts land in .skycache/ffi/rust/ (a .skyi with HM types, plus a Rust _bindings.rs), and codegen calls them like any other function.

Why rustdoc JSON? It's the crate's own compiler-verified description — names, signatures, generics, types. Parsing that is far more reliable than guessing from source, and it tracks the crate version exactly. No hand-written FFI means no drift and no human error in the binding.

2What it can and can't reach

A function is auto-bindable when its shape can be named on the Sky side.

Reaches wellStruggles
free functions & constructors (new, from_*, parse)complex generics / lifetimes that don't map to HM
simple value types, strings, numbers, bytestrait-object–heavy or builder-macro APIs
"leaf" utility crates (uuid, semver, chrono, bytesize…)async / framework crates (axum, sqlx, reqwest…)
A subtle trap measured in practice A crate can bind many functions and still be unusable — e.g. a web framework might expose dozens of error/accessor methods but no way to construct the core Router/handler from Sky. Usability is about whether you can build the values you need, not the raw count of bound functions.

3The wrapper-crate pattern (for what auto-FFI can't bind)

Async and framework crates don't bind directly. The solution is a thin, fork-local wrapper crate that exposes a simple, nameable surface over the complex one. Four ingredients:

  • plain &str → Result / Dict String String signatures (things Sky can name);
  • a dedicated-thread async→sync bridge: spin up a current-thread tokio runtime on its own thread and block_on there — never block_on an ambient runtime;
  • delivered as a local file:// git dependency in ["rust.dependencies"];
  • a key insight: a wrapper fn(..) -> Result<T, String> binds as a synchronous Sky Result, so Sky call sites stay simple — no Cmd.perform re-threading.

Proven end to end by examples/rust/skyshop-rs — a real app binding async-stripe, firestore, and a firebase admin SDK through one wrapper crate.

A learned gotcha worth your time An FFI Result<_, String>'s error slot is unusable on the Sky side — the binding advertises String but codegen emits the runtime error type, so Err e can't be read as a string. The fix the project settled on: encode any status the Sky side inspects in the Ok payload (e.g. _status=…), never in the Err slot. Small rule, saves a confusing afternoon.

4The takeaway

Two tiers. Leaf crates: just add them to sky.toml and call them — the compiler does everything. Framework/async crates: write a small wrapper crate exposing a Sky-nameable, synchronous surface over a dedicated-thread runtime, and point a file:// git dep at it. Either way, you never hand-write an FFI binding.

Summary

  • Auto-FFI: sky.toml dep → rustdoc JSON → inspector → generated .skyi/_bindings.rs in .skycache/ffi/rust/. No hand-written glue.
  • Reaches leaf crates (free fns, ctors, simple types); struggles with async/framework/heavy-generic APIs. Usability = can you construct the values, not the bound count.
  • Framework crates → a thin fork-local wrapper crate: nameable &str → Result/Dict surface, dedicated-thread async→sync bridge, file:// git dep. (skyshop-rs proves it.)
  • Encode inspectable status in the Ok payload — the FFI Err slot's String isn't readable on the Sky side.
