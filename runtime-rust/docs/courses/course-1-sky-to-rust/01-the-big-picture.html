Lesson 1 · the map From Sky text to a Rust binary in five stages

Before we zoom into any one part, you need the map. A Sky program becomes a Rust binary by passing through five stages. Learn their names and what each one hands to the next, and every later lesson has a place to hang.

1The pipeline at a glance

The first three stages are the front end — Sky shares them with its Go backend. The fourth, codegen, is where the Rust backend lives. The fifth is just cargo.

Key idea Each stage narrows ambiguity. The parser recovers structure; the canonicaliser resolves which println you meant; the solver decides every type; codegen turns that fully-known program into Rust text. Codegen can be "dumb" precisely because the three stages before it removed all the guesswork.

2What each stage produces

Stage 1 — Lex & Parse → Source AST

The lexer turns raw characters into tokens (and applies the layout rule, so indentation becomes structure). The parser assembles tokens into a tree of expressions and declarations. Names are still bare — a println is just the word "println", not yet resolved to anything.

Entry: src/Sky/Parse/Module.hs · parseModule :: Text → Either ModuleError Src.Module. Lexer/layout in src/Sky/Parse/{Space,Keyword,Primitives}.hs.

Stage 2 — Canonicalise → Canonical AST

Now every name gets resolved against imports and scope. A call head becomes one of a few precise things — the ones you'll see constantly in codegen:

NodeMeans
Can.VarKernel mod nameA built-in stdlib op (e.g. "String" "fromInt"). Codegen routes these to runtime functions.
Can.VarTopLevel mod nameA user (or stdlib-as-Sky) top-level function defined elsewhere.
Can.VarLocal nameA parameter or let binding in scope.

Entry: src/Sky/Canonicalise/Module.hs · canonicaliseWithDeps → Can.Module.

Stage 3 — Type-solve (Hindley–Milner) → SolvedTypes

The solver infers a type for every expression with no annotations required, and records two things codegen will read:

  • an environment: name → its resolved type;
  • region types: a source location → the type inferred there. This lets codegen ask "what's the type right here?" and pick the correct Rust type — crucial for empty collections, closures, and generics.

Entry: src/Sky/Type/Solve.hs · the SolvedTypes record carries _stEnv (env) and the region map.

Stage 4 — Codegen (lowering) → Rust source

This is the Rust backend. The orchestrator generateRustProject walks the canonical modules, consults SolvedTypes, lowers each definition to Rust text, and writes a whole cargo project to sky-out/Rust/: main.rs, one file per module, a Cargo.toml with only the features the program needs, the copied runtime crate, and any FFI bindings.

Entry: src/Sky/Generate/Rust/Project.hs · generateRustProject (called from src/Sky/Build/Compile.hs). The lowering itself lives under src/Sky/Generate/Rust/Builder/ — Lesson 4 tours it.

Stage 5 — Build → Binary

Plain cargo build on the generated project. If the codegen did its job, this just works — which is the whole thesis of the backend (Lesson 12).

Why a separate runtime crate? Codegen never emits the implementation of String.fromInt or println — it emits a call to a hand-written Rust function in runtime-rust/src/sky_runtime/. Keeping the heavy logic in a real, testable Rust library (not in generated strings) is what makes the output sound and small. The compiler copies that crate into every project at build time.

3One program, all the way down

Let's make it real with the smallest interesting program. It prints the number three.

src/Main.sky

main = println (String.fromInt (1 + 2))

After Stage 2 (canonical AST), sketched as a tree — note the bare names are now resolved kernels:

Def "main" []
  Call (VarKernel "Log" "println")        -- println is the Log kernel
    [ Call (VarKernel "String" "fromInt")    -- String.fromInt
        [ Binop "+" (Int 1) (Int 2) ] ]

After Stage 3, the solver has typed every node: 1, 2, 1+2 : Int → String.fromInt (…) : String → println (…) : Task Error (), so main : Task Error ().

Stage 4 routes the kernels. kernelToRust in Builder/Kernel.hs is a big lookup table from (module, name) to a Rust function name:

-- Builder/Kernel.hs (kernelToRust)
("String", "fromInt") -> "string_from_int"
-- println is special-cased in ExprEmitter → log_println

And here is the real emitted Rust (from sky build --backend rust, lightly trimmed). The Task-typed main becomes a sky_main that returns a SkyTask value, driven at the entry by block_on:

sky-out/Rust/src/main.rs

pub fn sky_main() -> SkyTask<()> {
    log_println(string_from_int(1 + 2))
}

fn main() {
    match block_on(sky_main()) {
        SkyResult::Ok(_)  => (),
        SkyResult::Err(e) => { eprintln!("{:?}", e); std::process::exit(1); }
    }
}

Codegen also emits a thin local wrapper for each kernel it uses, which forwards into the runtime crate — so log_println in main.rs is just sky_runtime::log::log_println(msg). The real work is the hand-written runtime fn:

// runtime-rust/src/sky_runtime/string.rs
pub fn string_from_int(i: i64) -> String { format!("{}", i) }
Corner case Why is println special-cased while String.fromInt goes through the plain table? Because println takes many arguments and joins them with spaces (like Go's), so ExprEmitter builds that join itself instead of a one-to-one call. You'll meet a handful of these special-cased kernels (Task.andThen, deferred let _ = effects, currying) in Lesson 5 — they're the interesting part of codegen.

Summary

  • Five stages: Lex/Parse → Canonicalise → Type-solve → Codegen → cargo build.
  • The first three are the shared front end; each removes ambiguity so codegen can be straightforward.
  • Codegen (generateRustProject) emits calls into a hand-written runtime crate, then writes a whole cargo project to sky-out/Rust/.
  • A kernel call is routed to a Rust fn by kernelToRust (Builder/Kernel.hs); a Task-typed main runs via block_on.
