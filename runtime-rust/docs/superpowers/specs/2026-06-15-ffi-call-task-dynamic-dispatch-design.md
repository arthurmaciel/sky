# Ffi.callTask dynamic dispatch — design

**Divergence id:** `ffi-call-task-dynamic-dispatch`
**Disposition:** DOCUMENT_INTENTIONAL (a deliberate no-reflection guard).
**Status:** at-parity-by-design for the dynamic shape; the "deferred to sub-project D" framing is a misattribution and is retired here.

## Problem

Go's `Ffi_callTask` (`runtime-go/rt/rt.go:3491`) is a runtime **registry**
lookup keyed by `fmt.Sprintf("%v", name)` over auto-generated Go-package FFI
bindings — a deferred-thunk, effect-unknown, reflection/`any` path *by
construction*. Rust's FFI is direct native monomorphic kernel calls with no
registry. The Rust backend carries two stub polyfills (`ffi_polyfills.rs`)
whose doc-comments tell **two different stories** for what is really one
boundary, and the README divergence row + panic-ledger row repeat the
inconsistency. The asker wants the canonical story and the correct disposition.

## Answered questions

**1. Intentional divergence or future-work-with-a-buildable-path?**
**Intentional, permanent.** Go's callTask semantics *are* string-named dynamic
dispatch into an effect-unknown binding table — a reflection/`any` surface by
construction. There is no faithful Rust analogue without reintroducing the
`Box<dyn Any>`/registry this backend exists to avoid. Mirroring that risk
surface is a defect, not parity (runtime-rust/CLAUDE.md). Permanent intentional
divergence, not a deferral.

**2. Which of the two justifications is canonical?**
Neither as written — they conflate **three** concerns. Canonicalised:

| Cause | What it is | Disposition |
|---|---|---|
| (a) **dynamic shape** — non-literal name or args | Same for `callPure` AND `callTask`. The only way to faithfully serve it is Go's `%v`-string registry = reflection. | **DOCUMENT_INTENTIONAL** — refused by the no-reflection guard. |
| (b) **static-shape `callTask` peephole** absent (no mirror of the `callPure` one) | A literal `Ffi.callTask "K" [lit]` currently hits the polyfill instead of a direct kernel call. | **YAGNI / not future-work** — zero reachable call sites (see below). |
| (c) **"Task-emitting FFI kernels" / "sub-project D"** | The stale framing in `ffi_call_task_polyfill`'s comment. | **Retired** — a misattribution. Effectful kernels already work via `Ffi.kernel` direct dispatch, never via `Ffi.callTask`. |

The `ffi_call_pure_polyfill` story (dynamic-vs-static) is the correct one and
applies verbatim to callTask. The `ffi_call_task_polyfill` "deferred to
sub-project D / needs Task-emitting kernels" story is wrong.

**3. Should a static-shape `Ffi.callTask` peephole be added (symmetric to callPure)?**
**No.** No well-typed Sky program emits even a static-shape `Ffi.callTask`:
the stdlib's effectful kernels (`Http.*`, `Task.*`, `Db.*`, `Time.now`, …) are
declared as `Ffi.kernel "Name"` aliases and resolved by the Stage-4 call-site
rewrite / the zero-arg-kernel + direct-dispatch paths — they never route through
`Ffi.callTask`. callTask exists for **auto-generated Go-package bindings**,
which are out of scope on Rust. A peephole here would pre-build for an unreached
call site. YAGNI: keep the gap documented until (if ever) a Rust-native
effectful-FFI producer chooses to emit static-shape callTask.

**4. Can the dynamic shape arise from well-typed Sky, and is the `panic!` an
acceptable compiler-bug-contract guard?**
The dynamic shape **is** type-checkable (name is `String`-typed), so it is NOT
provably dead the way a pure invariant is — a user *can* write
`Ffi.callTask computedName args`. Therefore the runtime `panic!` is **not** a
clean compiler-bug-contract guard for callTask (unlike Go's `Ffi_kernel` panic
at `rt.go:3537`, which guards a build-time rewrite that genuinely cannot leave a
residue). The principled floor is a **compile-time rejection** (see Q5), not a
runtime panic. Until that lands, the polyfill panic is a documented intentional
divergence with an actionable refactor message — acceptable as a temporary
bridge, but the root-cause fix is compile-time.

**5. Is there a total alternative to the panic?**
**Yes, and it is the correct fix: reject the dynamic shape at compile time** —
the same mechanism that turns an `any`-typed record field into a Sky-level
`error[Rust]:` build error (README §998). The Haskell codegen
(`exprToRustInner`) already pattern-matches the static peephole shape; the
*else* branch for `("Ffi","callTask")` / `("Ffi","callPure")` with a non-literal
name should emit a structured compile-time diagnostic ("dynamic-dispatch
`Ffi.callTask`/`callPure` is unsupported on target=rust — use a string-literal
kernel name, or `Ffi.kernel`") instead of falling through to a runtime-`panic`
polyfill. That converts a no-total-value runtime guard into a total
compile-time rejection — strictly better under no-panic, and entirely
in-boundary (`src/Sky/Generate/Rust/`). This spec records it as the **eventual
root-cause fix**, but does not schedule it as IMPLEMENT here because (a) it
touches the codegen pattern-match surface for both callPure and callTask and
needs its own fixture-locked change, and (b) no reachable Sky program triggers
either polyfill today, so there is nothing to verify a behavioural change
against. Filed as the narrow future-work item.

**6. Scope of "Task-emitting FFI kernels" and is any in-boundary?**
The phrase describes Go's auto-generated Go-package bindings (`FfiGen.hs`),
which require a Go runtime and are out of scope (README §38). Rust-native
effectful FFI is a **separate mechanism** (`Sky.Build.Rust.Ffi`) that does not
route through `Ffi.callTask`. So the `Ffi.callTask` divergence is **orthogonal
to, and never blocks,** Rust-native effectful FFI. "sub-project D needs
Task-emitting kernels" is a false dependency.

**7. Should the README rows be split / re-dispositioned?**
**Yes.** Row §33 (`Ffi.callTask` dynamic dispatch — "unsupported", unticked
future-work box) should move into the **Intentional divergences — by design,
NOT future work** block with the rationale "mirroring Go's reflect/`%v`-registry
`any` surface is a defect, not parity." The panic-ledger row §748 should be
re-worded from "deferred to sub-project D — needs Task-emitting kernels" to the
same dynamic-dispatch-guard rationale as the §747 callPure row (the two are one
boundary). No new unchecked future-work box is warranted — the only real
future-work item (a compile-time rejection replacing the runtime panic, Q5) is
narrow and gated on a real trigger.

## Disposition + rationale

**DOCUMENT_INTENTIONAL.** The callTask/callPure **dynamic** path is a deliberate
no-reflection guard: serving it faithfully would require Go's `%v`-string
registry, i.e. the `Box<dyn Any>`/reflection surface this backend exists to
refuse. It is at-parity-by-design, not a deferral. The misleading "sub-project
D / Task-emitting kernels" framing is retired; effectful kernels reach Rust via
`Ffi.kernel`, and callTask's real consumer (Go-package bindings) is out of
scope. A genuine future-work sliver exists (replace the runtime panic with a
compile-time rejection, Q5) but is gated on a reachable trigger and is not
scheduled here.

## Principle check

- **No shared-stdlib / Sky-source / Go-backend / upstream-examples edits.** This
  spec only re-documents (README + spec + a Rust-side test). The eventual
  root-cause fix (Q5) lives in `src/Sky/Generate/Rust/` — in-boundary.
- **No new Any / panic introduced.** The existing `panic!` is pre-existing and
  flagged as the temporary bridge; nothing here adds a panic vector. The
  recommended trajectory *removes* a panic (compile-time rejection).
- **Verifiable here.** The "zero callTask source sites" claim is a one-line grep;
  the existing `#[should_panic]` tests in `ffi_polyfills.rs` already lock the
  guard's message.
- **Go-parity:** this is below behavioural parity in the priority order —
  security/correctness/soundness (no reflection) win. The dynamic path is the
  only place Go and Rust differ, and Go's choice there is the defect.
