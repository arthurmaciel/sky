## `runtime-rust/src/sky_runtime/live/mod.rs` — exploitable
- **high/weak-crypto** new_sid() — mod.rs:443-462 (used as the session-cookie value at mod.rs:746/760/770; consumed as the sole session authenticator by sid_from_cookie + store.get)
  - exploit: The session id is the only bearer credential for a Sky.Live session, yet it is NOT generated from a CSPRNG. Entropy = SystemTime::now() nanos XOR a process-local AtomicU64 counter that starts at 0, run through splitmix64 (an invertible bijection — it adds zero entropy, only diffusion). The real input space is (wall-clock ns at session creation) × (small monotonic counter). An attacker who can bound when a victim's session was created (observable via response timing, a shared event timeline, or by forcing session creation themselves to learn the current counter region) can brute-force the 64-bit-pair down to a feasible search. Worse, event_handler accepts the target sid from the POST BODY (parsed.session_id, mod.rs:907) when no cookie is sent, and CSRF double-submit (csrf.rs) compares cookie-token==header-token WITHOUT binding either to the sid. So an attacker who holds a valid CSRF pair for their OWN session can POST to /_sky/event with a GUESSED victim sessionId in the body and dispatch arbitrary Msgs into the victim's TEA loop / read their rendered state over the hijacked session — a full cross-session takeover that CSRF does not stop. The code comment 'not a security token' is precisely the defect: it IS the session authenticator. Note gen_token() in csrf.rs already uses OsRng, so a CSPRNG is in-crate and unused here.
  - fix: Generate the sid from the OS CSPRNG (reuse csrf::gen_token() or OsRng.fill_bytes into 16 bytes → 32 hex). Drop the clock+counter scheme entirely. Additionally, bind dispatch to the cookie sid only: in event_handler require sid_from_cookie and remove the parsed.session_id body fallback (or, if kept for proxies, bind the CSRF token to the sid so a token valid for session A cannot drive session B).
- **medium/auth-bypass** event_handler — mod.rs:907 (let sid = sid_from_cookie(&headers).unwrap_or(parsed.session_id))
  - exploit: The mutating event endpoint resolves the target session from the request body's sessionId whenever the cookie is absent. CSRF (csrf_middleware) only proves the caller possesses a self-consistent cookie/header token pair — it never ties that pair to the sid being acted upon. Combined with the predictable sid above, a caller with any valid CSRF pair can address another user's session by sid. Even independent of sid entropy, this is an authorization gap: possession of a CSRF token is not authorization to act on an arbitrary session.
  - fix: Authenticate dispatch by the cookie sid exclusively; never trust a body-supplied sessionId for session selection. If a body sessionId must be honored for non-browser senders, gate it behind a per-session secret carried in the cookie and constant-time compared, and bind the CSRF token to that sid.
- **low/dos-unbounded** sse_handler heartbeat task — mod.rs:857-867 (and the per-GET driver spawn at mod.rs:798)
  - exploit: Each GET with a valid (or guessable) sid spawns a per-session mpsc(1024) driver (mod.rs:786-807) and each SSE attach spawns a detached 15s-heartbeat loop (mod.rs:859) that only ends when tx.send errors. An unauthenticated client can mint sessions at will (no auth on the page GET) and open many SSE streams, accumulating driver tasks + heartbeat tasks + session-store entries; the 60s TTL sweep (mod.rs:985) reclaims memory-store sessions only after the idle TTL (default 30 min). No per-IP / global session-count cap exists, so a burst creates a large transient footprint of goroutine-equivalent tasks and 2KB+ SSE padding writes.
  - fix: Cap concurrent sessions (global + per-remote-addr) and concurrent SSE streams per session; shorten the unattached-session reaper; tie heartbeat-task lifetime to an explicit session-close signal so an abandoned stream is cleaned promptly.
- **low/dos-unbounded** console::ingest reachability — mod.rs:1033 route + console.rs:163 (body: String, no DefaultBodyLimit) ; CSRF-exempt via csrf::is_exempt_path (csrf.rs:129)
  - exploit: /_sky/observability/ingest is CSRF-exempt and, by default (SKY_INGEST_TOKEN unset — the documented dev/single-process default), unauthenticated. Any client can POST JSON telemetry that fold_log folds into the operator console's in-RAM log/error/span rings, polluting the operator dashboard and amplifying per-entry memory. The body is only bounded by axum's implicit 2MiB default (no explicit DefaultBodyLimit layer like /_sky/event has), so an attacker controls up to ~2MiB of attacker-authored 'logs' per request to flood the rings.
  - fix: Add an explicit DefaultBodyLimit to the ingest route; fail the gate closed (require SKY_INGEST_TOKEN) when production_from_env(), rather than leaving it open by default; bound the rings and rate-limit ingest.

## `runtime-rust/src/sky_runtime/crypto.rs` — weak-but-bounded
- **low/weak-crypto** crypto_md5 (l69) / crypto_sha1 (l61)
  - exploit: No injectable attack reachable from this file alone — MD5 and SHA-1 are exposed as pure `String -> String` kernels. A Sky caller who (mis)uses them for password hashing or signature integrity would get collision/preimage-weak digests. This mirrors the Go oracle exactly (deliberate interop surface for checksums/legacy), so it is a documented parity contract, not a defect introduced by the Rust backend. The hashes themselves are computed correctly.
  - fix: None required for parity. If hardening is wanted later, add a `sky doc` deprecation note steering security-sensitive callers to sha256/hmacSha256/Auth.hashPassword. Do not silently change behaviour (breaks cross-backend digest equality).
- **low/weak-crypto** crypto_aes_key_from_password / crypto_chacha_key_from_password (l288-298), PBKDF2_ITERS=100_000 (l191)
  - exploit: PBKDF2-HMAC-SHA256 at 100k iterations is below the OWASP 2023 recommendation (600k for SHA-256). An attacker who exfiltrates a derived-key blob plus a known salt can brute-force a weak password ~6x faster than a modern target. Bounded: it exactly matches the Go oracle (runtime-go/rt/crypto_aead.go:35 pbkdf2Iterations=100_000), so it is a cross-backend compatibility contract — raising it here would make Rust-derived keys incompatible with Go-derived keys for the same password+salt. No amplification or bypass; cost is a constant factor on an already-CSPRNG-salted derivation.
  - fix: Treat as a backend-wide policy decision (must move in lockstep with Go to preserve key interop), not a Rust-local change. If raised, bump both backends together and version the on-disk format. Within this file, the derivation is correct (right algorithm, 32-byte output, salt honoured).

## `runtime-rust/src/sky_runtime/jwt.rs` — weak-but-bounded
- **low/weak-crypto** jwt.rs:9 jwt_encode_hs256 / jwt.rs:23 jwt_decode_hs256
  - exploit: Unlike auth.rs's signToken/verifyToken (which enforce secret.len() >= 32 at lines 106/141), the Sky.Core.Jwt HS256 entry points apply NO minimum-secret-length floor. A Sky app that calls Jwt.encodeHs256 with a short/empty/low-entropy secret (the unit tests themselves use 'my-secret' (9 bytes) and 'right'/'wrong') produces an HS256 token whose HMAC key is brute-forceable offline, letting an attacker forge arbitrary claims. This is not exploitable by the runtime in isolation — the secret is wholly caller-supplied and the weakness only materialises if the app passes a weak secret — and it matches the Go Sky.Core.Jwt primitive (which also defers the floor to Std.Auth). Hence bounded, not a runtime auth bypass.
  - fix: Either (a) document at the Sky.Core.Jwt surface that HS256 callers must supply a >=32-byte secret and route security-sensitive use through Std.Auth (which already gates), or (b) add the same `if secret.len() < 32 { return Err(...) }` floor to jwt_encode_hs256/jwt_decode_hs256 for defense-in-depth parity with auth.rs. RS256 paths are unaffected (asymmetric key supplied as PEM).

## `runtime-rust/src/sky_runtime/server.rs` — weak-but-bounded
- **medium/auth-bypass** build_request lines 316-322 (remote_addr) feeding fixed_window_allow at line 763 / middleware_with_rate_limit line 762
  - exploit: ServerRequest.remoteAddr is derived by unconditionally trusting the client-supplied `X-Forwarded-For` (first token) then `X-Real-IP`, and only falling back to the real TCP peer (ConnectInfo) when both are absent. There is NO trusted-proxy gating. When the server is exposed directly (default bind is 0.0.0.0, line 417) an attacker bypasses `Middleware.withRateLimit` entirely by sending a fresh `X-Forwarded-For: <random-ip>` header on every request — each request keys a distinct (key, client) window bucket, so the per-IP counter never reaches `limit` and the 429 path (line 766) is never hit. The same spoofing defeats any app-level IP allowlist / audit that reads `req.remoteAddr`. Secondary effect: rotating spoofed IPs inflates the `fixed_window_allow` HashMap (line 778) with up to (requests-per-window) distinct entries before `retain` (line 786) reclaims them at window expiry — a within-window memory amplification driven by attacker header values.
  - fix: Do not trust XFF/X-Real-IP by default. Gate the forwarded-header parse behind an explicit opt-in (e.g. SKY_TRUSTED_PROXY / a trusted-proxy CIDR list) and otherwise key remoteAddr on the ConnectInfo peer IP. When a proxy IS trusted, take the right-most untrusted hop of XFF rather than the left-most (which is fully client-controlled). Document that this matches Go's clientIP only when a trusted proxy is configured.
- **low/dos-unbounded** fixed_window_allow line 787 / rate_limit_allow line 809 (HashMap keyed on attacker-controllable client string)
  - exploit: Because the rate-limit key includes the spoofable remoteAddr (see finding above), an attacker rotating `X-Forwarded-For` values creates an unbounded set of map keys within a single window. `m.retain` only evicts entries whose window has elapsed (fixed_window) / refilled to full (token bucket), so under sustained high-rate traffic the map can hold roughly one entry per in-flight spoofed IP. Bounded by window length × request throughput rather than truly unbounded, but it amplifies the spoofing finding into transient memory pressure.
  - fix: Add an absolute cap on the rate-limit map size (LRU-evict or refuse-new past N entries), and resolve the underlying remoteAddr trust issue so distinct keys can't be minted for free by header rotation.
- **low/weak-crypto** serve_streaming_sentinel via sentinel_nonce (server_stream.rs:71-77), consumed at server.rs to_axum_response line 339
  - exploit: The streaming-response sentinel that gates whether a response body is interpreted as a chunked stream uses a per-process nonce derived from `std::collections::hash_map::RandomState` (OS-seeded SipHash keys, ~64-bit, not a CSPRNG token). A handler that reflects attacker-controlled bytes verbatim into the response body, combined with guessing the 64-bit per-process nonce and a live pending-handler token, could in principle dequeue/serve a pending stream handler. Practical impact is minimal (requires body reflection + brute force of a per-process value + a valid in-flight token), so this is defense-in-depth, not a live exploit.
  - fix: Derive sentinel_nonce from a CSPRNG (the runtime already pulls in entropy for Crypto.randomBytes) so the per-process gate is cryptographically unguessable rather than a hash seed.

## `runtime-rust/src/sky_runtime/db.rs` — weak-but-bounded
- **low/secret-leak** sky_err (line 11-13), reached from every db_* kernel's Err path
  - exploit: sky_err does format!("{}", e) on a sqlx::Error and returns it as the Sky Err(Error) value. On a DB-side constraint violation some sqlx/driver Display impls embed the offending bound value in the message (e.g. UNIQUE-constraint diagnostics). If a Sky app binds a secret (token, password hash, API key) as a positional param to db_exec/insertRow/insertFields and the statement trips a constraint, that secret can surface inside the returned Err string, which the app may then Log.* or render in a response body. Not a panic and not a direct log by this module — the value only reaches the Err slot — but it widens the secret-exposure surface beyond what a bound param should ever do. Matches the Go backend (parity, not a Rust-introduced regression).
  - fix: Sanitize sqlx::Error before stringifying for the Sky-visible Err: for Error::Database, surface only the driver code + a generic message (and the column/constraint name), never the offending value. Keep the verbose form behind a dev-gated SKY_DB_VERBOSE_ERRORS flag (ENV then SKY_ENV; unset/dev/development/local only).
- **low/injection** db_unsafe_find_where (line 883-894): format!("SELECT * FROM {} WHERE {}", qtable, where_clause)
  - exploit: where_clause is string-interpolated into the SQL with no validation (only the table is safe_ident-checked; args are bound). A Sky app that builds the where_clause from untrusted input is SQL-injectable. This is NOT a hidden backend flaw: the Sky-side name is unsafeFindWhere, the doc-comment states the hazard explicitly, and it mirrors Go's documented unsafeFindWhere trust model — the danger is opt-in and labelled at the call site. Flagged only so it is on record that the safety here is contractual (app must not pass untrusted where_clause), not enforced.
  - fix: No backend change required (intentional escape hatch with a self-documenting unsafe name). Optionally add a runtime reject of a where_clause containing a statement terminator (';') outside string literals as cheap defense-in-depth, but the real mitigation is the API name + docs already present.

## `runtime-rust/src/sky_runtime/live/store.rs` — weak-but-bounded
- **low/other** SqliteStore/PostgresStore/RedisStore::get — get(sid) reads & returns a session model keyed solely by sid (e.g. store.rs:143-149, 218-224, 305-308)
  - exploit: The store deserializes and returns the full session model for whatever `sid` string it is handed, with NO signature/MAC/integrity check on the cookie value. If an attacker can guess or forge a valid sid (predictable session id, or a sid not HMAC-signed at the cookie layer), they get another user's session model (Cold hydrate) verbatim. This is only safe IF the upstream cookie layer (out of these files) signs the sid and the generator is a CSPRNG. The store itself is a confused deputy: it provides no defense-in-depth and silently trusts the key. Mirrors Go, but the Rust backend's mandate is to be MORE sound.
  - fix: Document the hard dependency that sid MUST be a signed, CSPRNG-generated token validated before reaching the store, OR store an authenticated blob (e.g. bind sid into the serialized payload and verify on read). At minimum add a comment asserting the sid-trust contract so a future caller can't wire an unsigned sid in.
- **low/injection** open path construction — store.rs:115 `format!("sqlite:{path}?mode=rwc")`
  - exploit: `path` is the `[live] storePath` config / SKY_LIVE_STORE_PATH env. If it contains `?`/`&` it injects extra SQLite URI parameters (e.g. `x.db?mode=rwc&vfs=...&cache=shared`). Not reachable per-request from the network (operator-controlled config only), so impact is bounded; flagged for completeness because a templated DB path with attacker-influenced config (multi-tenant control plane setting storePath) would let URI-param injection alter open semantics.
  - fix: Percent-encode the path or use SqliteConnectOptions::new().filename(path).create_if_missing(true) (builder API) instead of string-formatting a URL, so a `?`/`&` in the path can never be reinterpreted as URI params.

## `runtime-rust/src/sky_runtime/live/hub.rs` — weak-but-bounded
- **low/injection** open_spill — hub.rs:721 `format!("sqlite:{db_path}?mode=rw")`
  - exploit: `db_path` is the SKY_CONSOLE_HUB_DB env / Sky `dbPath` arg. A `?`/`&` in it injects SQLite URI params. Operator/console-config controlled, not per-network-request, so bounded; still worth hardening because `mode=rw` (not `ro`) is intentionally a writable handle and URI-param injection could widen that further (e.g. flip cache/vfs).
  - fix: Use SqliteConnectOptions::new().filename(db_path).read_only(false).journal_mode(Wal) (typed builder) instead of formatting the path into the URL string, eliminating URI-param reinterpretation.
- **low/dos-unbounded** hub_read_service_stats — hub.rs:661-689 loops over distinct services, each running aggregate_service_stat (two queries capped at STATS_ROW_CAP=10_000)
  - exploit: One console request triggers (number-of-distinct-service_name) × 2 queries × up to 10k rows of in-memory aggregation. The set of service_name values is written by telemetry producers (sub-apps pushing to the spill); a producer that emits many distinct service_name values inflates the per-request work unboundedly in the number of services. Reachable only by an authenticated telemetry producer, and each query is row-capped, so impact is throughput degradation, not a crash.
  - fix: Cap the number of services aggregated per request (e.g. LIMIT on the distinct-services query) and/or aggregate in a single grouped SQL pass rather than N round-trips, matching Go's bound if Go caps it.

## `runtime-rust/src/sky_runtime/http_client.rs` — weak-but-bounded
- **low/dos-unbounded** do_request, http_client.rs:68 (resp.text().await)
  - exploit: do_request reads the entire response body via resp.text().await with no byte cap. http_get/http_post default followRedirects=true with maxRedirects=10, so a server the app POSTs/GETs (or any host reachable via a chain of up to 10 redirects it follows) can stream back a multi-GB body and drive unbounded heap allocation in the calling process — a memory-exhaustion DoS. There is no SKY_LIVE_MAX_BODY_BYTES-style cap on the OUTBOUND client side (the server side caps inbound POSTs, but this client does not cap inbound responses). Not attacker-reachable from an untrusted inbound request directly: the app picks the URL, so the trigger is a malicious/compromised upstream the app already calls (or a redirect target). Matches the Go backend's identical gap, so it is a shared defense-in-depth hole rather than a Rust-specific regression.
  - fix: Cap the read: stream the body with reqwest's bytes_stream() (or resp.content_length() pre-check) and abort with SkyResult::Err once an accumulated byte limit is exceeded (e.g. a configurable maxBodyBytes on HttpRequest defaulting to a few MiB, mirroring File.readFileLimit). At minimum reject Content-Length exceeding the cap before buffering.

## `runtime-rust/src/sky_runtime/email.rs` — weak-but-bounded
- **low/weak-crypto** send_smtp / Tls::Opportunistic (email.rs:515-517)
  - exploit: SMTP transport uses opportunistic STARTTLS (builder_dangerous + Tls::Opportunistic). A network MITM that strips the server's STARTTLS advertisement forces a plaintext session, leaking SMTP PLAIN credentials (cfg.user/cfg.pass) and the message body over the wire.   - exploit: host = format!("email.{}.amazonaws.com", cfg.region) and endpoint = https://{host}/v2/... interpolate cfg.region (a Sky String) into both the request URL and the signed Host header / Authorization credential scope with no charset validation. ## `runtime-rust/src/sky_runtime/server_stream.rs` — weak-but-bounded
- **low/weak-crypto** server_stream.rs:71-85 sentinel_nonce
  - exploit: The per-process anti-forgery nonce is derived from std::collections::hash_map::RandomState (SipHash key), not a CSPRNG. Worse, the two h.finish() values (lines 80,82) share continuing hasher state and are correlated, so effective entropy is below the claimed 128 bits. NOT remotely exploitable: the nonce is never emitted to any client (the sentinel body is consumed server-side in serve_streaming_sentinel and replaced by the real stream before anything is sent on the wire), so an attacker cannot observe it, and forging it blind requires guessing the OS-seeded SipHash-keyed output. Even a successful forge only diverts a response body to a handler popped by a token the attacker cannot have registered (self-inflicted app bug, not a cross-tenant or auth bypass). Defense-in-depth disambiguator, not a secret.
  - fix: If hardening is wanted, draw the nonce from getrandom/OsRng (already transitively available) into 16 bytes hex; or at minimum re-seed the hasher between the two finish() calls (rs.build_hasher() twice) so the two halves are independent. Functionally optional given the nonce never leaves the process.
- **low/dos-unbounded** server_stream.rs:48-56 pending_handlers / stream_senders global maps
  - exploit: pending_handlers() inserts a handler per stream-returning response and only removes it on a sentinel match in serve_streaming_sentinel (line 174). If server_stream_stream is invoked to build a ServerResponse that is then NOT returned through to_axum_response (e.g. the handler swaps it for a non-stream response), the entry leaks for the process lifetime. Bounded by the number of such code paths the app itself writes; not attacker-driven (the attacker cannot make the app construct stream responses it discards), so this is an app-shape footgun rather than a remote DoS.
  - fix: Acceptable as-is given it's app-controlled, not request-controlled. If tightened, cap the pending_handlers map size with a TTL/oldest-eviction, or tie handler lifetime to the response Drop.

## `runtime-rust/src/sky_runtime/system.rs` — weak-but-bounded

  - exploit: std::env::set_var/remove_var are documented as not thread-safe against concurrent READERS (any thread calling std::env::var, getenv in linked C, etc.).   - exploit: For a non-u8 fixed array element type `[T; N]`, N is parsed straight into a fixed-width Haskell `Int` via `reads`, with no range clamp (unlike the u8 path's digitsBeforeClose which clamps to 65536). ## `tools/sky-ffi-inspect-rs/src/main.rs` — weak-but-bounded
- **low/panic-untrusted** type_is_nameable, line 1217 (`&ty[start - 2..start]`)
  - exploit: `ty` is a Rust type string assembled by rustdoc_type_to_rust_str from rustdoc JSON (i.e. from a third-party crate the user `sky add`s). The slice `ty[start-2..start]` indexes raw bytes; `start` is guaranteed to sit on an ASCII byte (alpha/underscore), but `start-2` can fall inside a multibyte UTF-8 char. Rust allows non-ASCII identifiers (non_ascii_idents), so a crate-local opaque type whose qualified path places a 3-byte char (e.g. `€`) exactly one byte before an uppercase-initial token makes `start-2` bisect that char and panics the inspector with `byte index is not a char boundary`. Effect: the inspector subprocess aborts, failing `sky add`/`sky build` for that crate. Build-time DoS only; requires a deliberately/oddly-named type in a dependency.
  - fix: Test the `::` prefix on bytes without slicing on a possibly-non-boundary index: `start >= 2 && b[start-1] == b':' && b[start-2] == b':'` (b is already `ty.as_bytes()`), which never panics on UTF-8 boundaries.
