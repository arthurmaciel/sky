## `runtime-rust/src/sky_runtime/basics.rs` — high
- **high/soundness** basics_mod_by (l10): i64::MIN % -1 overflows: in Rust the `%` operator on i64::MIN with divisor -1 panics in debug builds ('attempt to calculate the remainder with overflow') and is UB-avoided-but-wrong in release. basics_mod_by(-1, i64::MIN) reaches `let r = n % divisor` directly (divisor != 0 guard passes), so a well-typed Sky program calling `modBy (-1) <minInt>` triggers a runtime abort. This is exactly the panic-from-well-typed-Sky class the Rust backend exists to eliminate. Go's int % -1 returns 0 with no panic.
- **high/correctness** basics_mod_by (l11): Divergence from Go's Basics_modByT (rt.go l1485). Go does `r := n % divisor; if r < 0 { r += divisor }` — it adjusts ONLY when the raw remainder is negative, irrespective of divisor sign. Rust adjusts when `(r<0 && divisor>0) || (r>0 && divisor<0)`. For a negative divisor the two functions differ: modBy (-3) 10 → Go returns 1 (raw 10%-3=1, not <0), Rust returns 1 + (-3) = -2. modBy (-3) (-10) → Go: raw -1<0 → -1+(-3) = -4; Rust: -1 is not >0 and the divisor<0 clause needs r>0, so returns -1. So Rust and Go produce different results for every negative-divisor case. The comment at l5-7 claims it 'matches Go's Basics_modByT' but it implements a different (Euclidean-style sign-of-divisor) modulo. Go-parity is broken.

## `runtime-rust/src/sky_runtime/crypto.rs` — high
- **high/security** crypto_rsa_sha256_verify (l122-140): Verify takes the WRONG key kind vs the Go oracle and the Sky stdlib contract. Sky declares `rsaSha256Verify pemPublicKey message base64Signature` and Go (rt.go:6494) parses a PUBLIC key (ParsePKIXPublicKey / ParsePKCS1PublicKey). The Rust impl calls `RsaPrivateKey::from_pkcs1_pem(&key_pem)` then `.to_public_key()` — it requires a PRIVATE key. A normal caller who holds only the public key (the entire point of verify) always gets `false`, so signature verification is silently non-functional. This is a verification-skipping/auth-defeating shape: any auth or webhook-signature check built on this either never passes (DoS) or, if a caller mistakenly feeds the private key, behaves unlike every other backend.
- **high/correctness** crypto_rsa_sha256_sign (l105-117) / crypto_rsa_sha256_verify (l131): Signature encoding diverges from Go and the Sky doc. Go sign returns STANDARD BASE64 (rt.go:6488) and verify base64-decodes (rt.go:6511); the Sky stdlib comment says 'standard-base64'. Rust sign emits HEX (l115 `format!("{:02x}")`) and verify hex-decodes (l131 `hex::decode`). A signature produced by the Go backend will never verify on Rust and vice-versa; round-trips only work Rust-to-Rust. Cross-backend / on-wire signature interop is broken.
- **medium/correctness** crypto_rsa_sha256_sign (l109): Sign accepts only PKCS#1 private keys (`from_pkcs1_pem`). Go (rt.go:6472-6482) accepts BOTH PKCS#1 and PKCS#8 PEM keys. A well-typed Sky program handing a PKCS#8 (`-----BEGIN PRIVATE KEY-----`) PEM — the modern default from openssl — gets `Err parse` on Rust but succeeds on Go. Go-parity gap.
- **high/correctness** crypto_random_bytes (l4-16): Return type contradicts the Sky stdlib signature. Sky declares `randomBytes : Int -> Task Error String` and Go returns a HEX-ENCODED String (rt.go:6533 `hex.EncodeToString`). The Rust kernel returns `SkyTask<E, Vec<i64>>` (a byte list), and codegen (Emitter.hs:176, ExprEmitter.hs:2876) propagates `Vec<i64>`. Sky believes the value is a `String`; any downstream `String.*` op, token use, or the doc-suggested `randomBytes 16` salt sees a list, not the hex string Go produces. Wrong value shape vs both the oracle and the declared type.
- **medium/security** crypto_random_bytes (l11) / crypto_random_token (l23): Missing the Go size bound enables an unbounded attacker-controlled allocation. Go errs for `size <= 0 || size > 1024` (rt.go:6536, 6555) and surfaces `Err InvalidInput`. Rust does `let count = n.max(0) as usize; vec![0u8; count]` with NO upper bound — a large `n` (e.g. from request input flowing into a token width) allocates gigabytes (DoS). The Sky type has an Error channel (`Task Error String`), so the bound belongs here exactly as in Go. Also `n as usize` truncates on 32-bit targets (the runtime targets WASM/embedded per CLAUDE.md), changing the count silently.
- **low/correctness** crypto_random_token (l18-34): Output encoding diverges from Go: Go `randomToken` returns RFC4648 URL-safe base64 (rt.go: `base64.RawURLEncoding`), Rust emits lowercase HEX (2 chars/byte). Different string for the same entropy width; cross-backend tokens are not comparable and the URL-safety/length contract differs.

## `runtime-rust/src/sky_runtime/decimal.rs` — high
- **high/soundness** decimal_add/decimal_sub/decimal_mul (l68-70): `a.0 + b.0`, `a.0 - b.0`, `a.0 * b.0` use rust_decimal's std operator impls, which `panic!("Addition overflowed")` / `"Subtraction overflowed"` / `"Multiplication overflowed"` (verified rust_decimal 1.42.1 src/arithmetic_impls.rs l161/l232/l259) when the 96-bit mantissa / Decimal::MAX (~7.9e28) is exceeded. A well-typed Sky program — `Std.Decimal.mul (fromString "1e20") (fromString "1e20")` or repeated doubling — aborts the process. This is the existential 'no runtime panic from well-typed Sky' violation and is the #1 target.
- **high/correctness** decimal_add/sub/mul (l68-70) + decimal_percent_of/add_percent/sub_percent (l132-140): Go-parity break: Go's kernel calls shopspring/decimal `.Add`/`.Mul`/`.Sub` (decimal_kernel.go l171/l178/l185), which is big.Int-backed and does NOT overflow at 7.9e28 — the same Sky program returns a value in Go but panics in Rust. The percent helpers compound the issue (`pct.0 * base.0`) for ordinary money math where pct*base can exceed the bound. The Rust backend is meant to be MORE sound than Go, not less.
- **high/soundness** decimal_to_minor (l57-63): `d.0 * RD::from(factor)` uses the panicking `*` operator. `factor` can be up to i64::MAX (~9.2e18 ⇒ ~19 significant digits); multiplying a moderately large decimal by it overflows Decimal::MAX and panics. The author defensively used `checked_pow` for the i64 factor (l61) but then routed it through the un-checked decimal `*`, leaving the panic vector open one line later.
- **low/correctness** decimal_from_minor (l35) + decimal_to_minor (l58): `(places.max(0) as u32)` truncates BEFORE the `.min(RD::MAX_SCALE)` clamp. For `places` ≥ 2^32 (e.g. 4294967296) `as u32` wraps to 0, so a huge scale silently becomes scale 0 (in from_minor) / pow exponent 0 (in to_minor) rather than the intended MAX_SCALE clamp. Not a panic, but a silently-wrong result; the comment claims the value is clamped to MAX_SCALE, which is false for these wrapped inputs. (decimal_to_minor has no clamp at all — relies on checked_pow saturating.)
- **low/efficiency** decimal_format_with (l163-171): `grp_sep.chars().rev().collect::<String>()` re-reverses the (attacker/caller-supplied) group separator on EVERY 3-digit group inside the loop. For a large integer part this is O(digits/3 * sep_len) repeated allocation on a formatting hot path; hoist the reversed separator out of the loop once. Bounded by the MAX_SCALE/format width cap so not a DoS, purely wasteful.

## `runtime-rust/src/sky_runtime/live/mod.rs` — high
- **high/security** serve_live router build (l934-964) + render_page_full (l116-134) + client.js (__skyCsrfToken l3): The Go backend wraps the mux with a default-ON double-submit-cookie CSRF middleware (live.go:3449 CSRFMiddleware) and injects a per-session csrfToken into the page so /_sky/event POSTs carry X-Sky-Csrf validated server-side. Result: /_sky/event is fully CSRF-open. The only protection is the SameSite=Lax cookie (l527), which is strictly weaker than Go's defense-in-depth and the mandate to mirror Go with MORE security. This is a security regression vs the Go oracle.
- **medium/security** serve_live page render / response headers (l960-964, l522-539): Go sets Referrer-Policy: strict-origin-when-cross-origin, an X-Frame-Options / CSP frame-ancestors cross-origin allow-list, and related hardening headers on every Live response (live.go:3562-3574). The Rust backend emits none of these — no Referrer-Policy, no frame-ancestors / X-Frame-Options, no X-Content-Type-Options. The console-link clickjacking / framing surface that Go closes is open here.
- **medium/security** event_handler (l830-846): No request-body size cap. Go applies http.MaxBytesReader(w, r.Body, maxBody) on /_sky/event (live.go:3915), default 5 MiB and configurable via SKY_LIVE_MAX_BODY_BYTES / sky.toml [live] maxBodyBytes. The Rust handler takes axum::body::Bytes with no DefaultBodyLimit override and no SKY_LIVE_MAX_BODY_BYTES honouring, so an attacker can POST an arbitrarily large body (bounded only by axum's silent default) — a memory-amplification DoS vector and a parity gap (the configurable knob is silently ignored).
- **medium/security** page handler msg_tx channel (l737) + event_handler dispatch (l885-888) + drive_session recv loop (l388): The per-session Msg channel is unbounded_channel(). A client (or any party who can reach /_sky/event with a valid/forged session cookie) can fire events faster than drive_session folds them through update()/diff(), growing the queue without bound — unbounded memory growth per session, a DoS. Combined with the missing CSRF gate above, this is reachable cross-site. Go's event path is rate-limited / CSRF-gated upstream; the Rust unbounded queue has no backpressure or cap.
- **low/security** sid_from_cookie (l988-1000) -> page (l703,l717,l727) -> page_response Set-Cookie (l522-529): The session id written back into the Set-Cookie header is taken verbatim from the inbound cookie value (cookie_sid = sid_from_cookie, client-controlled) on a Live/Cold/None hit, with no charset validation before re-emission. Go validates/normalises session ids; mirroring that (reject non-hex sids, fall back to new_sid) would harden the round-trip. - **low/correctness** event_handler form-data parse (l873-879): For non-submit events the args are coerced via value_to_string, which for a JSON object/array yields its JSON serialization (other.to_string()). The OnBool arm in dispatch.rs treats only the literal "true" as true; a client posting a numeric/boolean JSON arg (e.g. true vs "true") for a checkbox event silently resolves to false. Go's wire path decodes the typed checked Bool. Minor divergence — only affects malformed/alternate-shaped senders, since the bundled client posts the expected string shape.

## `runtime-rust/src/sky_runtime/math.rs` — high
- **high/soundness** math_abs (l25): `x.abs()` on i64 panics in debug builds and overflows (UB-free but wrong) in release when `x == i64::MIN`, since `-i64::MIN` is not representable. `math_abs : Int -> Int` is reachable from well-typed Sky as `Math.abs (-9223372036854775808)`, so a well-typed program can trigger a runtime abort. This violates the no-runtime-errors existential constraint. Use `x.wrapping_abs()` (or `unsigned_abs` per the Sky contract), matched to Go's behaviour and documented.
- **medium/correctness** math_floor/math_ceil/math_round/math_trunc (l33,34,38,39): `x.floor() as i64` uses Rust's saturating float->int cast: NaN->0, +inf->i64::MAX, -inf->i64::MIN, out-of-range finite saturates to the bounds. Go's `int64(math.Floor(x))` of an out-of-range/NaN float is implementation-defined and does not saturate identically, so Rust and Go yield different integers — a silent Go-parity divergence. Since `math_nan()`/`math_inf()` are exposed kernels, `Math.floor (Math.nan)` is reachable well-typed Sky returning 0 in Rust vs Go's unspecified value. Total (no panic, good for soundness) but a correctness/parity gap; define and align the contract with the Go oracle.
- **low/correctness** math_min/math_max (l27-28): `math_min`/`math_max` use `<=`/`>=` on `T: PartialOrd`. With a NaN f64 operand, `a <= b` is false so `math_min(nan, b)` returns `b` while `math_min(a, nan)` returns `nan` — the result depends on argument order and NaN is silently dropped or propagated. Total (no panic), but a potential silent wrong-result vs Go's min/max NaN convention; cross-check and pin with a test.
